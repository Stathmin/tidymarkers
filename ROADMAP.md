# tidymarkers — roadmap (открытая работа)

Только незакрытое. Полный ретроспективный инвентарь (что уже есть, с обоснованиями и
ссылками) — в `INVENTORY.md`; история изменений — в `NEWS.md`.

Обозначения: `[ ]` очередь · `[~]` частично · `[x]` сделано · `[—]` проверено и
**отложено** (с причиной) · `[!]` проверено и **опровергнуто**.

**Формат пункта.** Каждый открытый пункт отвечает на четыре вопроса:

- **правка** — что именно менять и где (файл и функция, а не тема);
- **проверка** — чем закрывается (тест-файл, id в `dev/check-criteria.R`, артефакт);
- **блокер** — что не даёт начать, и чем он снимается;
- **следствие** — что меняется, если пункт НЕ делать (почему он вообще стоит).

Пункт без одного из четырёх — не готов к работе и остаётся в своей секции как
описание, а не в очереди.

> **О провенансе.** Ниже отдельно помечено, что **открыто прочитано**, а что
> известно только по идентификатору. Правило то же, что в коде: **DOI/название —
> это провенанс, а не доказательство.** Число попадает в `inst/extdata/` только
> если оно прочитано из скачанного файла, и у него есть скрипт
> `data-raw/<paper>.R`, который утверждает его против собственных итогов статьи и
> падает при расхождении. Где такого утверждения построить нельзя — файл не
> пишется, и причина записывается.

## Приоритет (пересмотрено после второго внешнего разбора)

**Наука раньше архитектуры.** Большой слой ZA (S3 `Scheme`, `tidygraph`-схема
решений, `TrackSpec`, `yardstick`) откладывается в пользу двух пунктов, которые
дают правильность, а не форму кода:

1. **Z7** (намеренные вторые мисматричи) — главный рычаг для слабых transition
   SNP в KASP/ARMS. Сейчас такой случай **помечается**, но не **исправляется**; это
   надо закрыть первым.
2. **Z8** (калибровка) — без внешнего якоря никакая специфичность не доказуема.

Порядок до калибровки: `ZW0` (инварианты) → `ZW1` (фальсифицируемые гейты) →
`ZW2`/`ZW3` (провенанс движков, независимый Tm-оракул) → `Z7` → `Z8`.
Из ZA до калибровки — только **шаг 1–4** `ZA6` (это контракты данных, а не
косметика); шаги 5–6 (`tidygraph`, грамматика графиков) — **после** Z8; шаги 7–8 —
по мере надобности.
Дисциплина «рефакторинг не сдвигает вердикт» (`f494a50`) сохраняется: каждый шаг
из `ZW` и `Z7` принимается только с неизменными вердиктами на золотом наборе.

**Что это значит на практике.** `ZW0`/`ZW1`/`ZW4` закрыты, `ZW2` остаётся
незакрытым одним пунктом (проводка штампа в `Evaluation`, см. `ZW2.2`), `ZW3` —
межмодельная сверка сделана. Поэтому **вход в Z7 открыт с той стороны, с которой
его можно закрыть**: параметр строится на `z7_engine_probe.csv` (margin match−off),
а не на одной эффективности, и до решения `Q2` позиция якоря остаётся спорной.

### Открытые решения (`data-raw/proposed/*.proposal.md`)

Восемь `*.proposal.md` — это решения по уже влитым данным, а не код. **Из них в
`R/` не применено ничего**; `merge-proposals.R --apply` их не переносит.
Правило: пока решение не принято, артефакт говорит «данных нет», а не
«данные против» — так устроены тесты, которые это утверждают.

Каждое решение закрывается **тремя строками**: (1) `Status:` → `decided` и дата,
(2) какая правка в `R/` следует из решения (файл и функция) либо явное «в `R/` не
меняем» с причиной, (3) тест, который это утверждает. Предложение без третьей
строки остаётся открытым.

### Q1. Снять три заявки, которые код всё равно не подтверждает

Не научное решение: данные уже говорят «нет», код говорит обратное.

- **правка.** `R/marker_taqman.R`: комментарий L46-53 выдаёт `TAQMAN_MISMATCH_DG
  <- 1.5` за установленный порог, а `taqman_status.proposal.md` показывает, что
  ни одна открытая статья не печатает ни порога ΔG, ни ΔCt matched vs mismatched.
  Заменить обоснование на «правило без измерения; см. proposal», пометить
  критерий `evidence = "rule_of_thumb"` (он уже там) и **не** выдавать вердикт
  «проба не дискриминирует» как научный факт — только как порог пакета.
  `R/marker_readout.R` — таблица `notes` уже честно пишет
  `"isothermal amplification kinetics not modelled"` для LAMP; правка там не
  нужна, нужна ссылка из `marker_taqman.R` на неё. `polyploid_scope` — alias
  `homolog`/`homoeolog` в доке (уже есть в `specificity_policy`).
- **проверка.** Три существующих теста: `test-taqman.R` (комментарий-контракт:
  порог не назван измеренным), `test-readout.R` (`simulated = FALSE` для LAMP),
  `test-polyploid-scope.R` (нет единого polyploid rate). Всё зелёное — значит
  правка текстовая, и вердикты не сдвигаются.
- **блокер.** Нет.
- **следствие.** Пользователь читает «порог 1.5 kcal/mol» как физическое свойство
  TaqMan, и `unknown` в отчёте выглядит как недоработка модели, а не как
  отсутствие данных.

## ZA. Целевые интерфейсы и швы (codebase-design)

Это план перестройки **модулей и швов**, а не список функций. Принцип:
табличные данные — `tibble`/`vctrs`; поведение — S3-generic; граф —
`tidygraph`; рисование — грамматика `ggplot2`; внешний движок — adapter с
`capabilities()`. Не тащить `R6`/`data.table`; не превращать поведение в
data-frame только ради «tidy».

**Состояние: шаги 1–4 частично сделаны.** `Evaluation` (единый
`marker_evaluation_table()` + статус `pass|fail|unknown|not_applicable`),
`MarkerContext`/`ReactionConditions`/`Engines` (`marker_run_context()`,
`marker_engines()`) и реестр критериев (`criterion_spec()`) существуют. `Scheme`
как S3-адаптер — нет: вызывается `design_<m>_marker()`. Шаги 5–8 заперты на `Z8`.
Наука (`Z`, `Z7`) стоит выше всего этого (см. «Приоритет»).

### ZA1. Целевой путь вызова

```r
context <- marker_context(
  genome, variants = NULL, population = NULL,
  conditions = reaction_conditions("pcr"), engines = marker_engines()
)
scheme <- marker_scheme("caps")
m  <- scheme$design(snp, context)
ev <- scheme$evaluate(m, context)
tr <- scheme$tracks(m, context)
dc <- scheme$decision()
ro <- scheme$readout(m, context)
```

Сегодня: `marker_scheme("caps")` работает, но возвращает строку реестра, а не
объект с `$design()`; вызов идёт через `design_caps_marker(genome, snp)`.

#### ZA2.1. `capabilities()` объявлена, но никто её не спрашивает

Граф (`graphify`, 2026-10-21) даёт узлу `capabilities()` (`R/marker_core.R:353`)
**степень 2**: `marker_core.R` (contains) и `cli::cli_abort()` (calls). Вызовов
из `R/` нет.

Правка: ни один дизайнер и ни один `gate_*` не читает `capabilities()`, поэтому
гейт не умеет ослабнуть, когда движок не имеет возможности (`blast` без `rBLAST`,
`duplex_dg` без OligoArrayAux). Все такие места сейчас — литералы.
Проверка: `test-capabilities.R` — фейковый движок с `blast = FALSE`;
соответствующий гейт возвращает `unknown`, а не `pass`.
Блокер: нет. Делать **до** `Z0.1` и `Z5.1`: без этого ослаблять нечего.
Следствие: таблица возможностей остаётся документацией, а не контролем; тест
на «движок отсутствует» проходит по счастливой случайности.

#### ZA2.2. `marker_generic_checks()` живёт в файле методов рисования

Определена в `R/marker_plot_methods.R:118`, вызывается только из
`marker_primer_checks()` (там же, `:439`). Граф: степень 6, ни одного вызова из
`R/marker_checks.R` — хотя по смыслу это проверка, и `marker_checks.R:244`
вызывает свою ветку отдельно.
Правка: перенести в `R/marker_checks.R`, оставив в plot-файле только
адаптер раскладки.
Проверка: существующие тесты plot/checks без изменений проходят.
Блокер: нет.
Следствие: чтение `marker_checks.R` не даёт полной картины проверок.

### ZA5. Что не делать tidy/ggplot

- `Scheme` и `Engines` — поведение, S3-generic, не data-frame.
- `DecisionSchema` — графовые данные + state; рисование отдельным adapter.
- `Readout` — typed result (`simulated`, `lod`, `maf`, `stderr`), не ggplot.
- Не вводить seam для одного adapter (deletion test): если удаление модуля
  просто возвращает сложность одному caller, это pass-through.

### ZA7. Acceptance / test surface

- Вызовы в тестах идут тем же швом: `marker_context()` → `scheme$design()` →
  `scheme$evaluate()` → `scheme$tracks()`/`scheme$readout()`.
- Contract-test: каждая схема реализует `design/evaluate/tracks/decision/readout`.
- `NA` никогда не становится `pass`; `unknown` не считается успехом.
- У каждого criterion один bounds-object и `source`/`calibrated`.
- Fake thermo/specificity engines дают deterministic тесты без OligoArrayAux.
- Golden-тесты: criterion-id, evaluation-table и track-rows; не пиксели.
- После каждого шага — `graphify update .` и `dev/check.R`.
- Граф как ориентир, не как доказательство: узлы `stage_gates`/`stage_relax`/
  `stage_tiers` (`R/marker_criteria.R:599/604/608`) в граф не попадают — это
  локальные векторы, поэтому о трёх параллельных картах стадий граф молчит.
  Проверять чтением, а не запросом.

### Y1. Конструктор технологий (композиция из блоков)  [фундамент]
- **Сейчас:** схема = `scheme_def_<m>()` + `design_<m>_marker()`, гейты/тиры/проверки
  декларативны, семейства `KASP_CHECK_PRIMER`/`_SITE`/`_AS` (`marker_criteria()`);
  `marker_tech(schemes|preset|exclude, costs=)` уже параметризует набор схем в пуске.
- **Цель:** технология собирается пользователем из **блоков-фильтров и параметров**,
  а не пишется с нуля: готовые блоки (состав/шпильки/димеры, повторы, специфичность,
  3'-якорь, ампликон, readout), и из них — «гига-KASP» = KASP + доп. ограничение
  (напр. «праймеры подлиннее», «шпильки строже»). Набор доступных методов — параметр
  пуска, а не зашитая логика (уже принцип `marker_tech`).
- **Ограничение: композируемость ≠ всеядность.** Свободная комбинация
  фильтров может собрать химически бессмысленную технологию (блок «гомополимеры»
  для SSR, где повторы — цель; `MGB`-правила на CAPS-гель). Поэтому:
  1. **Блок декларирует, к каким химиям применим** (`applies_to = c("kasp",
     "arms", …)`); реестр `marker_filter_blocks()` несёт это поле.
  2. **Конструктор отказывает на несовместимой смеси** (`marker_technology()`
     возвращает ошибку с перечнем несовместимых пар), а не предупреждает.
  3. **Собранная пользователем технология по умолчанию `calibration_evidence =
     "rule_of_thumb"`** (см. `ZW4`), даже если все блоки взяты из
     откалиброванных пресетов: порог из контекста ≠ порог из калибровки этой
     комбинации.
- **Артефакт:** `marker_technology()` (конструктор: семейство + блоки + параметры),
  реестр блоков `marker_filter_blocks()`, `marker_technologies()`; валидация, что собранная
  технология — корректный DAG (`expect_dag_invariants()`).
- **Формат обмена — декларативный, не код.** Технологию для шаринга сериализовать в
  **YAML** (блоки + параметры как данные); R-файл — только для локальных кастомных
  дизайнеров и не является форматом обмена (шаринг R-файла = выполнение чужого кода).
- **Зависимость:** перестройка DAG (§W) — реестр проверок/гейтов/семейств уже единый.
- **Генерализация до `marker`.** Модуль давно шире «просто KASP»: там, где семантика
  не KASP-специфична (проверки, критерии, фрагмент-маркеры, размерные маркеры),
  функции/файлы/описания следует обобщать до `marker` (маркер-агностичный API и доки),
  оставляя `marker_`-префикс только действительно KASP-специфичному. Ломающих
  переименований не делать: вводить общие имена с алиасами/депрекейтом.

### Y2. Цели по области (goal = что угодно из группы сцепления)

### Y3. Специфичность/off-target — политика технологии  [начато]
- **Сейчас:** `in_silico_pcr()`, `specificity_seed()`/`primer_hits()`,
  `KASP_UNGATED_CHECKS`; off-target гейтится лишь у части схем; `select_with_ladder()`
  ослабляет мягкие гейты.
- **Не «с ноги»:** off-target не всегда порок — для qPCR/мультиплексной детекции
  внеплановая амплификация бывает частью задачи, для FISH неспецифичность ожидаема.
  Поэтому специфичность — **политика технологии**
  (`specificity_mode = "unique" | "homeolog-aware" | "multicopy" | "off"`), а не
  глобальный жёсткий гейт.
- **Цель:**
  1. **Нет чистой пары — нет маркера.** Сейчас при отсутствии чистой пары берётся
     ранговый лидер с предупреждением (§H); для специфичности это недопустимо —
     технология, требующая уникальности, возвращает **NO marker с причиной**, а не
     помеченный off-target'ами маркер. Инвариант «off-target-гейт не в relax-наборе»
     проверяется тестом, как `expect_dag_invariants()`.
  2. **`homeolog-aware` (пшеница).** **Прочитано по исходникам PolyMarker**
     (VERSION 1.3.3, commit `d4a4578`). Правила с method+line и тест
     (`polymarker_design_rules.csv`, `data-raw/polymarker-source.R`,
     `test-y32-homeolog.R`). Ошибка прочтения исправлена: **AS-праймер различает
     аллели, а не субгеномы.**
     - `primer_3_all_strings` ставит AS-праймеры на SNP
       (`seq_original[pr.snp_pos]`, `SEQUENCE_FORCE_LEFT_END`) — это **ось аллеля**.
     - Субгеномная специфичность — это **общий праймер**: для каждой позиции маски
       класса `chromosome_specific` / `almost_chromosome_specific` он получает
       `right_pos => pos`, т.е. `SEQUENCE_FORCE_RIGHT_END` на это основание —
       это **ось субгенома**.
     - Позиция считается субгеном-специфичной только когда **все остальные**
       субгеномы отличаются от целевого И все геномы представлены
       (`different == expected_snps && from_group == genomes_count`).
     - Нет такой позиции → общий праймер без force (`chromosome_nonspecific`):
       ассей есть и генотипирует, но он **не** субгеном-специфичен.
     - В конструкции **нет поля**, говорящего, *какой* праймер несёт субгеном:
       это подразумевается только самим force.
     Следовательно:
     - AS 3′-мисматч к гомеологам — **следствие**, а не механизм.
     - Артефакт обязан различать **`allele_base`** (AS 3′) и
       **`subgenome_anchor`** (3′ общего праймера) отдельными полями. Сейчас —
       отдельные колонки `fam_3p` / `hex_3p` / `common_3p`, но не одно поле.
     - Если на общем праймере нет диагностического основания — маркер
       `multicopy` с предупреждением, а не тихо «специфичный».
     - **Эмпирическая проверка оси** (1000 реальных ассеев Grewal 2020): AS 3′
       принимает ровно 2 значения на каждую пару аллелей (и это именно аллели,
       или их комплементы в reverse-режиме 491 ассея), а `common_3p` — ≥3 значения
       на ту же пару. Если бы 3′ общего праймера нёс аллель, было бы наоборот.
     - `unique | multicopy | off` этот случай не выражают — нужен явный
       `homeolog_diagnostics` в кандидате.
     - **Benchmark, не реимплементация:** PolyMarker — эталон для wheat
       genome-specific KASP и источник правил с провенансом; его логику не
       переписывать.
  3. **3'-end-aware off-target:** позиция и число несовпадений у 3'-конца, а не только
     совпадения по длине.
  4. **Ленивая оценка поверх ранга:** идти по списку и гонять in silico PCR **пока не
     наберётся k прошедших**; перед ним — дешёвый префильтр уникальности 3'-k-меров.
  5. **Индекс — решить до старта (масштаб).** §O откалиброван под Arabidopsis (120 Mb);

  «нашлась ли force-позиция». Отсутствие диагностического основания на общем праймере
  → `multicopy` + предупреждение.
- **Проверка:** расширение `test-y32-homeolog.R` на Grewal 2020 (1000 ассеев): AS 3′
  ровно 2 значения на пару аллелей, `common_3p` ≥ 3; тест, что поле заполняется для
  всех ассеев и `NA` только там, где основание не диагностично.
- **Блокер:** нет (правила и данные уже в `inst/extdata/`).
- **Следствие:** `Y3` пункт 2 закрывается по артефакту; без этих полей
  `homeolog_diagnostics` остаётся догадкой.

#### Y3.5. Индекс под 15 Gb: замер памяти до коммита
- **Правка:** выбор бэкенда фиксируется по замеру памяти индекса на пшеничном геноме
  (FM `Rsubread` / BLAST / хеш 3'-12-меров); свой код — только 3′-aware пост-фильтр.
- **Проверка:** замер RSS и времени построения индекса, записанный в `data-raw/`
  с командой и версией; решение в ROADMAP со ссылкой на файл замера.
- **Блокер:** нужен пшеничный FASTA (~15 Gb) локально.
- **Следствие:** «ленивая оценка» (Y3 п.4) не повисает; до замера её не начинать.

#### Y3.6. Опция дополнительных сборок
- **Правка:** финальные кандидаты прогоняются по списку сборок/пангеному, а не только
  по одной.
- **Проверка:** тест на двух сборках, где вторая содержит паралог: кандидат,
  прошедший первую, помечается по второй.
- **Блокер:** `Y3.5` (вторая сборка стоит того же замера памяти).
- **Следствие:** маркер не выглядит уникальным из-за одной сборки.

### Y4. Многоцелевое ранжирование и Парето-фронт
- **Сейчас:** жёсткие гейты + лексикографические тиры (узкое место `min`);
  `marker_risk()` low/medium/high; `marker_solve()` идёт по стоимости.
- **Цель:** трёхмерный фронт — **цена**, **качество ассея** (включая информативность в
  панели) и **риск потери сцепления** (нужна генетическая/физическая дистанция или
  карта рекомбинации); выдавать **Парето-фронт** с рекомендованной точкой, а не одно
  «лучшее» решение. Четыре оси не вводить — фронт плохо читается.
- **Артефакт:** `marker_pareto()`; `marker_informativeness()` (по доступным гаплотипам/VCF —
  маркер, различающий двух родителей, может быть бесполезен на популяции; **входит в ось
  качества**); модель дистанции/рекомбинации; интеграция в отчёт `marker_solve`.

#### Y4.1. `marker_informativeness()` — первым
- **Правка:** новый `R/marker_informativeness.R`; по VCF/гаплотипам — доля различаемых
  пар линий, PIC/ожидаемая гетерозиготность на доступной выборке; `NA`, если выборка
  мала, и явная причина.
- **Проверка:** тест на синтетическом VCF с известным PIC; тест, что маркер,
  различающий только родителей, получает низкую информативность на популяции.
- **Блокер:** нет.
- **Следствие:** ось качества в `Y4.2` перестаёт быть заглушкой.

#### Y4.2. `marker_pareto()` — после информативности
- **Правка:** новый `R/marker_pareto.R`; три оси (цена, качество+информативность,
  риск сцепления), фронт + рекомендованная точка; интеграция в отчёт `marker_solve`.
- **Проверка:** тест на фронте с известным ответом (доминируемая точка не попадает
  во фронт); тест, что рекомендованная точка входит во фронт.
- **Блокер:** `Y4.1` + `Z8` (риск сцепления без калибровки — `rule_of_thumb`).
- **Следствие:** `Y2.1` получает «цена-качество» вместо лексикографического `min`.

### Y5. Инпуты: что уже есть и что доработать
- **Уже есть и работает индексно (переписывать не нужно):** `read_variants_vcf()`
  (vroom / `VariantAnnotation`, регион по tabix), `read_genome_fasta()` + `marker_genome()`
  (индексированный `Rsamtools` / `BSgenome`, `chrom_map`, `seqids`), `read_transcripts()` +
  `haplotypes_from_alignment()`, `marker_chunk()`, аннотация (`marker_annotate.R`).
- **Уточнённый список доработок:**
  1. ридер **GenBank** (`read_genbank()`) — быстрый, с индексацией;
  2. импорт **файлов заказа праймеров** (IDT и родственные) — `read_primer_orders()`;
  3. **глубина из VCF** (DP/AD) как вес уверенности в генотипе: низкопокровные
     гетерозиготы штрафовать/исключать (`marker_context(depth=)`);
  4. обратная «сборка пары»: `find_mate_primer()` — по заданному первому праймеру и
     мишени найти второй;
  5. выравненный фасад разнородных входов к одной паре `targets` + `context`.
- **Фасад для внешних пайплайнов:** вход VCF+DP → готовые кандидаты маркеров.
- **Стабильность фасада.** Для использования пакета как зависимости нужен стабильный
  фасад (`marker_context(depth=)` и т.п.) и честная пометка о нестабильности API
  (`lifecycle`/`experimental` с явным предупреждением в доке).
- **Гексаплоид и глубина.** Низкая глубина и картирование на паралоги портят не только
  гетерозиготы, но и сами вызовы гомозигот: слабую уверенность штрафовать/исключать, а
  не ограничиваться фильтром гетерозигот.

#### Y5.1. `read_genbank()`
- **Правка:** новый ридер с индексацией (не читать файл целиком на каждый запрос).
- **Проверка:** тест на фрагменте GenBank: число фич и диапазоны совпадают с тем,
  что напечатано в `LOCUS`/`FEATURES`; тест на запрос по региону не читает файл
  полностью (счётчик обращений).
- **Блокер:** нет.
- **Следствие:** область (Y2) может приходить из GenBank, а не только из VCF.

#### Y5.2. `read_primer_orders()`
- **Правка:** импорт файлов заказа праймеров (IDT и родственные форматы).
- **Проверка:** тест на сохранённом файле заказа — имена, последовательности и
  модификации совпадают построчно; файл обрезан в `inst/extdata/` (не весь заказ).
- **Блокер:** нет.
- **Следствие:** обратная задача (Y6) и `find_mate_primer()` получают вход для
  уже заказанных праймеров.

#### Y5.3. `marker_context(depth=)`
- **Правка:** DP/AD как вес уверенности; штраф не только гетерозигот, но и гомозигот
  при низкой глубине (Y5 «гексаплоид и глубина»).
- **Проверка:** тест на VCF с известными DP: гомозигота DP=1 не проходит как
  уверенная; вес монотонно падает с глубиной.
- **Блокер:** нет.
- **Следствие:** стабильный фасад для внешних пайплайнов (`Y5.5`).

#### Y5.4. `find_mate_primer()`
- **Правка:** по первому праймеру и мишени — поиск второго.
- **Проверка:** тест на известной паре с ампликоном известного размера; тест, что
  найденный праймер проходит те же гейты, что и в прямом дизайне.
- **Блокер:** нет.
- **Следствие:** обратная задача (Y6) закрывается для случая «есть один праймер».

#### Y5.5. Фасад `targets` + `context`
- **Правка:** выравненный фасад разнородных входов (VCF+DP, GenBank, сборка) к одной
  паре `targets` + `context`; пометка `experimental` в доке.
- **Проверка:** тест, что два разных входа с одинаковым содержанием дают одинаковый
  `context`; тест на предупреждение о нестабильности API.
- **Блокер:** `Y2.1`.
- **Следствие:** пакет можно использовать как зависимость.

### Y6. Валидация, бенчмарки и обратная задача
- **Минимальный регресс-харнесс — уже в фазе A.** Без набора опубликованных маркеров
  не понять, улучшил ли новый off-target-гейт и ранжирование результат или просто
  изменил его. Первый источник ground truth — уже отобранные/опубликованные маркеры из
  смежного проекта; полный набор — здесь.
- **Опубликованные маркеры — только положительные примеры (survivorship bias).**
  «Не хуже опубликованного маркера» — ложная цель: опубликован тот, кто сработал.
  Для калибровки `Z8` нужны и **провалы**. Поэтому в наборе с самого начала:
  `outcome = worked | failed | unknown`, и статьи с перечнем неудачных ассеев
  предпочтительнее статей с удачными маркерами (см. `Z8`).
- Набор известных случаев, где «правильный» маркер уже **опубликован** (KASP/CAPS/…);
  регресс-харнесс; аргумент для публикации. `inst/extdata/validated_markers/`,
  `dev/bench-markers.R`. **Выход остаётся порядковым** (`usable`) до достаточного
  числа отрицательных примеров — см. `Z8`.
- **Обратная задача — «проверить текущий набор маркеров»:** на вход подаётся готовый
  маркер (явная последовательность, фрагмент или один праймер из пары + мишень), тип
  маркера задан пользователем; тул прогоняет его по приёмке (состав, структура,
  специфичность, дискриминация), **не проектируя заново**. Тесты — на опубликованных парах.
- **Проверка:** `outcome` заполнен для каждой строки набора; число `failed` растёт
  (это признак работы, а не регресса); вердикт остаётся порядковым.
- **Блокер:** `Z8` (без отрицательных примеров калибровка невозможна).
- **Следствие:** `Z8` и `Y4.2` получают данные; без него пороги остаются `rule_of_thumb`.
